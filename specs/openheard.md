# OpenHeard 设计规范

本文只写约束代码的内容。代码改了不会过时的东西不在这里。场地数据属于部署配置，评估过程和操作者处境属于调研笔记，操作步骤属于 README。

## 这是什么

一本由机器可读来源填写的通联日志，不靠人打字。

数字网络发布逐次会话的 feed。模拟中继什么都不发，所以用只收不发的接收机把静噪开启变成事件。人只补机器无法知道的那部分。

## 需求

自动记录每一次通联，模拟和数字都要，不论经过哪个中继或哪个网络。

一条性质推导出其余全部：**自动化来自记账的那一方，从不来自电台。**

## 已定死的决定

这些在写代码前定死，因为事后改代价最高。

**数据模型从第一次迁移就带齐 LoTW 要求的字段。** 包括频率、模式、波段、双向 RST 和网格。已经装了真实通联的 schema 最难改，而这一点正是排除在现成点名工具上开发的原因。

**在此之上还存 QTH、设备、天线、功率和高度。** 存它们不花什么代价，通联结束后却再也拿不回来。

**Web 界面用 React 19 加 Ant Design 6。**

**不做原生客户端。** 采集守护进程无头运行，通联过程中没人打字，浏览器够用。只有出现明确的野外离线需求才重新考虑，而且先试 PWA。

**不重复造轮子。** LoTW 签名调 TQSL 命令行。DXCC 实体判定用现成的 cty.dat 库。Web 层用标准框架。自己写的只有采集管道、聚类和 ADIF 组装，因为没人写过这三样。

**后端用 TypeScript 跑在 Node 上，HTTP 层用 Hono，库用内置的 `node:sqlite`。** 运行时依赖只有 Hono 那两个包，没有要编译的原生模块。

**聚类阈值取 120 秒，来自实测。** 实测 BrandMeister 46001 组 9636 个静默间隔：p50 10 秒，p75 36 秒，p90 102 秒，p95 177 秒。取 120 秒，约 8% 的相邻发射会被切成两段，而两分钟以内的停顿留在同一次对话里。

**聚类阈值仍然是一个值，不分模拟和数字。** 中继挂起时间只影响模拟侧，上面那组数来自数字侧。模拟侧攒够量之前拆成两个数等于拍一个，所以等模拟那边也有实测再拆。

**管理端整个挡在口令后面。** 会话是签名 cookie，HttpOnly，服务端不存状态。采集入口走自己的 Bearer token，不看会话。

**这条推翻了原来「只监听回环所以不用认证」。** 站在楼下拿手台时要用手机确认通联，而那正是这个系统存在的场景，回环地址够不着手机。既然管理端迟早要离开回环，认证就不是可选项。

**监听地址是配置项，默认仍是回环。** 默认开到全网等于升级之后悄悄把管理端暴露出去。

**人会改的设置从界面改，api 写回配置文件，守护进程盯着文件跟上。** 不在两个进程之间另开一条接口，配置文件本来就是共用的那一份。必须落盘，只改内存的话 launchd 下次重启就悄悄变回去。守护进程盯的是目录不是文件，因为原子替换之后是新的 inode，盯着文件的 watcher 会永远停在旧的那个上。

**`dbPath`、监听地址和三个密钥不进界面。** 它们要么一改就要重启整套，要么改错了就把自己关在门外。

**通联改过删过要留痕。** `qso` 是人判断出来的结果，重建不出来，覆盖和抹掉都不该不留痕迹。记的是改之前那一行的完整 JSON，和改动同一个事务。

**静噪的两个余量是配置项，不是常数。** 噪声本底和天线各地不一样，写死等于把一次部署的猜测烤进代码。调大了弱信号永远打不开，调小了噪声起伏就会伪造出发射。打开的余量要比关闭的至少大 2，中间那段是回差，挨太近会在门限上抖。两个余量都在设置页上，清空一格就回到缺省值，不是保留原来那个。

**电台此刻的样子要能在界面上看到。** 频率、校准出的静默基准、开关门限、此刻的噪声能量、静噪开没开、最近一次打开是什么时候。没有这些，「天线听不见」和「没人在发」长得一模一样，只能登录到机器上翻日志。守护进程每秒报一次，只留最新一条在内存里，不入库：它描述的是现在，重启之后本来就该重新问一次电台。

**模拟侧的录音要能回放。** 空中不带身份信息，对方呼号只能靠人回忆，写下来却听不回去等于白存。挂在会话后面，不进公开面。api 为此读配置里 `analog.recordingsDir`，那一段本来是守护进程那半边的，两个进程按规范跑在同一台机器上。

**ADIF 读得进来，判重按呼号加分钟。** ADIF 的时刻常常只到分钟，而这台机器记到秒，比死时刻的话同一份文件每导一次就多一份记录。只认这套系统用得上的字段，模式不是 FM 或 DMR、频率不在 2m 或 70cm 的一律跳过，不假装存下了自己表示不了的东西。

**聚类猜错时，人要能只结算其中几次发射。** 阈值是一个数，两段挨得近的对话会被并成一段。整段提升会把两边记成一条，整段忽略又把两边都丢掉。挑出属于这次通联的那几次，剩下的不结算，下一轮自己会分出去。不做合并：把两段已经分开的并成一条，值不回它的复杂度。只挑了几次时，开始时间和对方呼号按挑中的那几次重算，否则挑出后一段来记，记下的是前一段的人。

**结算的是人看过的那几次，不是点下去那一刻的整段。** 段 id 跟着最早那条发射走，段长了 id 不变。只凭段 id 结算的话，打开抽屉或选中之后才并进来的发射没人看过，就跟着入库或被忽略了。界面一律带上看到的那几次，后来的留在队列里。一次都没挑是错误，不当成整段。

**录音跟着发射行一起裁。** 每次静噪打开都写一个 wav，涨得比库里任何一张表都快，而且快多少取决于信道多热闹。发射行过了保留期被裁掉时，对应的录音一起删。已经提升或忽略过的行不裁，它们的录音也就留着。保留期比待确认窗口短时按窗口算，人还没处理的段连同录音都不裁。

**DMR ID 到呼号的对照只用自己收过的东西建。** BrandMeister 不是每条都带 SourceCall，缺的那几条用以前见过的补。不查 radioid.net：那要联网，而这台机器在国内、无人值守，为一个字段引一条外部依赖不划算。

**一次忽略好几段要在服务端一起做。** 一条一条调的话，每忽略一段就重新聚类一次，剩下那些段的边界和 id 都会变，后面几条全部 409。数字侧一大半是一两秒的空按，永远不会变成通联，一条一条点忽略没人受得了。

**手机是主要的屏，不是退路。** 规范里那个场景就是站在楼下拿手台、用手机确认。窄屏上待确认队列和日志都是一段一张卡，不是要横着拖的表，按钮占满一行。

**按钮的位置不能随数据变。** 这两页每 15 秒刷一次，按钮随数据出现或消失的话，手指落下去的那一刻底下已经换成另一个了。该禁用就禁用，不要拿掉。

**管理端界面由 api 在根路径上发出来。** 不发的话机器上只有接口，手机连过来是一片 404。静态文件不要会话，会话挡的是它背后的接口。前端路由一律回首页。

**从手机上用优先走 Tailscale，不是改 `0.0.0.0`。** 服务照旧只绑回环，Tailscale 从 tailnet 转进来并终结 TLS，够得着的只有自己的设备。改 `0.0.0.0` 是把登录口摆到整个局域网上，限速是最后一道不是第一道。

**健康检查不要会话，也不带计数、路径和磁盘。** 它的用处是一行 curl 当外部监控，要会话就用不上了。细节留在管理端的运维接口后面。

**登录口限速，其余不限。** 只有一个口令，猜中一次就是全部，而监听地址可以配到局域网。一个来源五分钟十次，超了回 429。别的路由不限速，因为它们都在会话后面，而这台机器只有一个人用。

**备份写完当场验。** 能打开、`integrity_check` 通过、行数和 schema 版本都对得上，否则不算备份成功。`VACUUM INTO` 没报错不等于文件能用。

**schema 版本记在 `PRAGMA user_version` 里，迁移在开库时跑。** 第 1 版就是最初那份 schema.sql，整份都是 `CREATE TABLE IF NOT EXISTS`，所以老库跑一遍不改任何东西，只补上版本号。库的版本比程序新就直接不开，否则旧代码会按旧的理解读新表。

**升级前备份，用 `VACUUM INTO` 而不是 `cp`。** WAL 模式下主库文件和 `-wal` 分两次读，`cp` 可能拷出半截。`qso` 是人判断过的结果，重建不出来。

**存下来的时间一律 UTC，界面显示的时区可选。** 存储、接口和 ADIF 导出全部是 Unix 秒 UTC，不在这几层做任何转换。界面是另一回事：换时区只改写出来的那串字，同一个时刻不变。缺省 UTC，因为业余无线电按 UTC 记。

**时间旁边必须写清楚是哪个时区。** 一串没有时区的数字比只用 UTC 更糟，看的人没法确定它是什么。表头、标签和输入框都跟着选定的时区改。

**输入也按选定的时区读。** 快速补录里打进去的那串字，就是标签承诺的那个时区的时间。换时区时把已经填好的值按旧时区读成时刻、再按新时区写出来，否则显示不变而含义变了。

**DMR 在 ADIF 里写成 `MODE=DIGITALVOICE` 加 `SUBMODE=DMR`。** 没有 `MODE=DMR` 这个取值。

## 系统能承诺什么

| 通联怎么走 | 机器能知道什么 |
|---|---|
| 模拟 FM 过中继 | 时间、时长、哪个信道，以及这次有没有我们 |
| 模拟 FM 的对方呼号 | 无 |
| DMR 过有公开 feed 的网络 | 本台发射的全部字段 |
| DMR 的对方呼号 | 另查话务组才有，而且可能为空 |
| DMR 过没有 feed 的网络 | 无 |
| HF，以后 | FT8 走 WSJT-X 的 UDP，SSB 无 |

模拟侧那个缺口是永久的，不是还没做完。模拟 FM 空中不带身份信息，任何接收机和任何软件都叫不出对方呼号。语音识别只能缩小缺口，所以系统必须在它关闭时依然完全可用。

## 形态

一个常驻守护进程负责采集并推给 API。浏览器和 API 对话。没有第三个可执行体。

采集、API 和数据库在同一台主机上。轮询要靠数据库判重，也要和接收机在一起，拆到云上只会多出一份要对账的数据。

守护进程只采集，API 独占数据库。守护进程把归一化后的发射事件推给 API，自己不开库，所以它在没有数据库的机器上也能单独验证。

判重在写入端做，键是 `Activity.id`，数字侧取 BrandMeister 的 `SessionID`。守护进程重复推送没有副作用。

取回的行在推送成功之前先落盘。热闹话务组只回溯几十分钟，API 停一会儿就再也取不回来。

守护进程同时跑数字轮询和模拟守听，两边推给同一个采集入口。模拟侧不单独开进程，因为它和数字侧共用配置、落盘和重试，拆开只会多一份要对齐的东西。

管理端有四个页面。待确认队列把观测到的对话补成通联。日志列表是正式记录的唯一入口，负责导出 ADIF。快速补录写没有任何观测的通联。运维页把健康状态和每次轮询的计数露出来。

**运维页不是可选项。** 无人值守时，取回多少行、解析出多少行、写入多少行是唯一能读到的东西，没有界面看它们等于白记。

**公开展示页是独立应用，不是管理端的一条路由。** 它只读，不暴露写接口，也不显示未确认的内容。独立是因为它将来要落在境外，而管理端留在本机。

模拟采集把一次静噪开启当作发射事件。接收机覆盖一段配置好的频谱，那段有多宽、里面有哪些信道，都属于部署配置而非设计。

**静噪判据用解调后高频噪声带的能量，不是音量。** 载波一来，鉴频器输出里的高频噪声塌下去，这就是调频静噪的原理。2026-09-15 在 438.700 上实测同一支电台，5 到 9 kHz 这条带有载波时 15.6 dB、无载波时 48.1 dB，差 32.5 dB。同一组数据里 300 到 3000 Hz 的话音带只差 20.3 dB，所以判据取噪声带，不取话音带。

解调交给 `rtl_fm`，守护进程只在它输出的音频上做判决。自己写鉴频器没有增量。

**一次只守一个频率。** 一支接收机同时只能调谐一处，多信道要靠跳频，而跳频期间漏掉的发射无法补回。先守一个。

数字采集在 feed 支持历史查询时一律轮询而不订阅。轮询漏一次会自愈，订阅断开则永久丢事件。

## BrandMeister 接入协议

2026-09-02 对线上服务实测确认。公开 wiki 没有这些内容，而且已发布的示例全都是错的，所以写在这里。

端点是 `wss://api.brandmeister.network/lh/?EIO=4&transport=websocket`。

**路径是 `/lh`，不是 `/lh/socket.io`。** 后者今天仍然能完成 engine.io 握手和 socket.io CONNECT，然后永远不推任何数据，也不报错。这个静默的成功是最难查的陷阱。

帧序列手工实现，不需要 socket.io 客户端库：

```
recv  0{"sid":...}               engine.io OPEN
send  40                         socket.io CONNECT，默认 namespace
recv  40{"sid":...}              CONNECT 确认
send  42["join","src_<DMRID>"]   订阅才要，不 join 就没有任何推送
recv  2       -> send 3          PING/PONG，约 25 秒，不回就被断开
recv  42["mqtt",{"payload":"<json 字符串>"}]
```

`payload` 是嵌在事件对象里的 JSON 字符串，需要二次解析。

上面那个 `join` 只属于订阅路径。`searchHouse` 不需要它，2026-09-14 实测不 join 直接查，照样返回 200 行和 `searchHouseComplete`。

房间由服务端过滤。前缀映射是 `{DestinationID: dst, ContextID: con, SourceID: src}`，只有这三个字段，且只支持相等。所以 `src_<DMRID>` 只推我们自己的会话，全球流量不会到达。

**轮询优于订阅。** CONNECT 之后发 `42["searchHouse",{"query":<rules>,"amount":<n>}]` 可以取历史。2026-09-08 实测一次 `amount: 200` 返回 200 行，跨度 53 天，全部属于该操作者。所以一次查询就能回溯约两个月。

**这条过滤规则同时挡住了对方。** SourceID 查询和 `src_` 房间都只给本台的发射。对方的呼号在他自己的行里。

要拿对方呼号，必须再按 `DestinationID` 查目标话务组。2026-09-14 实测 `DestinationID` 等于 91 的一次查询返回 50 行，含 22 个不同 SourceID。

`condition` 支持 `OR`，服务端按 OR 语义执行。**但每条规则必须单独发一次查询。** `amount` 是合并去重后的全局上限，所以热闹的规则会把安静的规则饿死。2026-09-15 实测把 91 组和 460 组 OR 在一起，`amount` 取 200。返回的 200 行全部来自 91 组，460 组一行都没有。单独查 460 组同样取 200 行，跨度是 3.9 天。

代价是回溯深度。amount 同为 200 时，src 查询跨 53 天。`DestinationID` 等于 460 跨 3.6 天，等于 91 只跨 51 分钟。话务组越热闹，同样行数覆盖的时间越短。所以轮询间隔必须按话务组定，不能用一个全局值。

join `dst_<TG>` 会收到整个话务组的推送，2026-09-14 实测 91 组每分钟约 20 行。所以话务组一律查历史，不订阅。

`searchHouseComplete` 会触发，在历史行发完之后到达。按行数上限提前退出就收不到它。它标记历史结束，不标记行流结束。已 join 的房间还会继续推实时行。

**`searchHouse` 的 `operator` 支持不完整，失败一律静默。** 2026-09-14 实测只有 `equal`、`not_equal` 和字符串字段上的 `contains` 被真正执行。`in`、`greater`、`less`、`begins_with`、`is_not_null` 都返回空集，不报错也不断连。字段名或 `condition` 写错同样静默返回空集。

数值字段的 value 必须是 JSON number。`DestinationID` 传 `"91"` 返回 0 行，传 `91` 返回 200 行。

`rules` 传空数组不报错，返回的是全网最新记录。所以过滤条件为空时必须自己拦住，不能把查询发出去。

历史行和实时行形状不同，这一点坑过一次：

| | 实时 | searchHouse |
|---|---|---|
| `Event` | `Session-Start` / `Session-Stop` | 没有 |
| `Start`、`Stop` | 数字 | 字符串 |
| 未知呼号时的 `SourceCall` | `""` | `null` |
| `Master` | 字符串 | 数字 |
| 链路类型字段 | `LinkType` | `LinkKind` |

所以解析器必须归一化，且不能假设 `Event` 存在。`SessionID` 是 uuid，用作幂等键。

取 `Session-Stop` 而不取 `Session-Start`。120 条样本里 Start 带呼号的占 40%，Stop 占 78%，而且只有 Stop 同时带起止时间戳。

`SourceCall` 经常为空，`SourceID` 从不为空。DMR ID 是这个 feed 里唯一可靠的身份。

`DestinationCall` 在话务组查询里恒为 null，不是呼号来源。SourceCall 为空时，`TalkerAlias` 不得用作后备。2026-09-14 实测 460 组，38 行缺 SourceCall，只有 3 行能靠 TalkerAlias 补出。

## 会话不等于通联

feed 每按一次 PTT 就产生一条会话。一条群组会话没有明确的对方，你喊一声可能没人应，也可能六个人接话。任何自动把会话变成通联的规则都会错得足够频繁，足以污染日志。

所以分两张表：

- `activity` 装观测到的每一次发射，自动写入，只追加，不手改
- `qso` 是正式日志，每一行都由人的判断产生

实测依据：抽样 67 次已完成会话，**超过一半时长在 0 到 3 秒**，属于误触 PTT、试机和短按。会话数远不等于通联数。

从 `activity` 提升到 `qso` 只需一次点击。自动化消灭的是打字，不是判断。手工录入的模拟记录直接写 `qso`，不带 `activity` 行，因为没有任何东西观测到它们。

**提升和忽略记在 `activity` 上，不记在 cluster 上。** cluster 是按阈值算出来的，边界会变。轮询随时可能补进一条更早的行，阈值实测出真值后也要改。任何一种都会让已处理的对话换一个 cluster id 重新出现，人再点一次就多一条重复的正式记录。

`activity` 有保留期，`qso` 没有。`activity` 丢了可以重新轮询取回，`qso` 不能。裁剪要跳过已经被提升或忽略引用的行。

## 把发射事件聚成通联

按间隔阈值聚类，把事件流切成一次次对话。阈值必须来自对真实流量的实测，不能拍定。

**先按信道分开，再在信道内部按间隔切。** 同一时刻本台可能既在中继上说话又在话务组上说话，那是两次不相干的对话。只按时间聚会把它们并成一段，提升出来的通联混着模拟信道和数字话务组。2026-09-15 实测到过一段 34 次发射的聚类同时含 BrandMeister 和 438.700。信道取话务组号，没有就取信道名，再没有就取频率。

判断哪次对话有我们，需要电台主动发一个标记。MDC-1200 用一次短突发携带 unit ID，且不会撞中继控制码。DTMF 已否决，因为它每一次过话都响，而且串码撞上控制码会向中继发指令。

**MDC-1200 解码器自己写。** 现成实现只有两支能用。Kaufman 那套 C 代码及其全部衍生是 GPL-2.0-only，没有 or-later，AGPL-3.0 吸收不了。SDRTrunk 许可证相容，但它是 Java，解码器耦合在自己的 DSP 框架里，没有喂音频吐文本的独立形态。TypeScript 的实现不存在。子进程管道在许可证上成立，但要装 sox 和 PulseAudio、还要现编一个 C 程序，和「运行时依赖只有 Hono 那两个包」冲突。

帧格式如下，2026-09-15 用 Kaufman 库和 OneOfEleven 固件两份互相独立的源码交叉核对过。

1200 bit/s，连续相位 2FSK，mark 1200 Hz、space 1800 Hz。`rtl_fm` 的 24000 Hz 正好每比特 20 个采样点。

**差分编码在同步字之前。** 空中比特是「变了没有」，要先逐位累积异或 `msg[n] = msg[n-1] ^ raw[n]` 才是消息位。同步字在消息位域里找。

同步字 `07 09 2A 44 6F`，40 位，MSB 先。极性有二义，要同时匹配它和按位取反的版本，命中取反版则其后 112 位整体取反。

同步字之后 112 位即 14 字节。解交织后前 7 字节是 `OP ARG ID_HI ID_LO CRC_LO CRC_HI 保留`。**ID 大端，CRC 小端，同一个 7 字节里两种字节序。**

**交织两端的比特序不同。** 空中 14 字节按 MSB 先拆成 112 位 `o`，取 `src[i] = o[(i % 7) * 16 + ⌊i / 7⌋]`，再把 `src` 按 LSB 先打包。两端写成同一个方向就永远对不上 CRC。

CRC 只覆盖前 4 字节，多项式 0x1021，初值 0，输入输出都反转，最后异或 0xFFFF。它对不上任何一个有名字的变体。

**前导码长度不是协议常数**，各家 24 到 128 位不等。不许依赖它做时序假设，只做同步字滑动相关，比特相位逐个采样偏移试。

**不做 FEC 纠错，CRC 不过直接丢帧。** 那部分是启发式门限译码，原作者只声称能纠三四位。

**只有 CRC 通过且 unit ID 相等才写 `mine`。** op 和 arg 不参与判定，Motorola 从未公开 opcode 表，能查到的值都是社区逆向结果。

**`rtl_fm` 不许加 `-E deemp`。** 判决比的是 1200 和 1800 两个音的能量，去加重按频率给增益会把这个比较压偏。

2026-09-15 在 438.700 上实测通过：8 次发射解出 7 次，unit ID 十六进制 6460，和电台屏幕上那栏一致。

实测到的 op 和 arg：`op=0x01 arg=0x80` 落在发射开头约 0.18 秒，`op=0x01 arg=0x00` 落在结尾前约 0.15 秒，对应固件里按下发和松开发两个位置。这两个值只用来读日志，判定仍然只看 CRC 和 unit ID。

**静噪打开之前要留一段前导缓冲。** 按下那一发在 PTT 后 30 毫秒就发完，而静噪要一两块音频才判得出来。不留前导时实测 8 次里有 3 次只解出松开那一发。

中继挂起时间会把快速往返合并成一条长事件，而且**越热闹合并越严重**。聚类恰好在最需要它的时候失效，所以聚类和标记不是二选一。

事件时长普遍偏长，多出来的大约是挂起时间。极短事件来自弱信号短暂顶开静噪，那是门限问题。

**全球话务组上聚类会退化成一大段。** 那种组从来不安静，间隔阈值永远切不开。2026-09-15 实测 91 组一次 200 行覆盖 0.88 小时，按 120 秒阈值聚成了 1 段 182 次发射。所以话务组查询只配本地实际在用的那些组，全球组不要配。

## 语音识别，可选

两段可分别开关。识别方负责转写一段**已经切好片**的发射。文字模型再从转写里提取候选字段。

提取约定如下：

- 只返回一个 JSON 对象
- 没有明确说出口的字段一律省略
- 不推断不编造
- 转写里只有噪声就返回空对象
- NATO 字母解码成大写无空格的呼号
- 口播功率归一成数字加 W

每个候选都必须经人确认才能进日志。模型名是配置项，不写死。

## RST

**中继通联不要推导信号强度。** 接收机听的是中继下行，而中继以固定功率转发。所以测到的电平只描述中继本身，以及我们这边的天线。同一个中继上每个人都一样。

**辨识度正好相反。** 中继把对方上行的噪声原样转发出去，所以弱台会在满功率下听起来很噪。音频信噪比因此携带对方的路径质量，而射频电平不携带。

直频两项都推导。中继上若音频信噪比稳定就用它推 R，否则默认 59。

音频信噪比取话音带减噪声带，也就是 300 到 3000 Hz 的能量减去 5 到 9 kHz 的能量。上面那次实测这个差是 12.2 dB。映射到 R 的分档要等真实流量，现在不定。

## 已否决

**把采集放在云函数上。** 早期实现是定时 Worker 加托管数据库，已退休。轮询要和数据库、接收机在同一台机器上，拆开就得对账。BrandMeister 那部分的协议细节记在上面，代码可以重写。

**在点名工具上开发。** 它的模型为点名而建，没有频率、模式、波段，没有 ADIF，还有一个在这里无对应物的主控呼号。许可证也会波及公开部署的服务。

**在现成 Web 日志本上开发。** 它一行都不用改，fork 只会增加合并负担。它保留为参考和后备。

**以桌面日志软件为基座。** 它们的重心是电台的 CAT 控制，没有对外写入接口，脚本灌不进去。

**把语音识别当必需项。** 它是加速器。系统必须在它关闭时可用。

## 许可证

**AGPL-3.0。** 选择依据是部署形态，不是偏好。

这个项目最可能被俱乐部拿去跑成公开网站。MIT、MPL 和 GPL 在这个形态下都不产生义务，因为它们由分发触发，而自己部署不算分发。AGPL 第 13 条专门覆盖这一点。

连带后果有两条。第一，它可以吸收 GPL 和 AGPL 的代码，所以将来直接用 OpenLogTool 的实现这条路是通的。第二，部分组织一刀切禁用 AGPL，采用摩擦是已知代价。

即便如此，**提示词仍然不要从 OpenLogTool 逐字抄**。提示词的可版权性无定论，照本文的行为约束清单重写一版，绕开整个问题。
